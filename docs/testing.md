# 测试功能与自动化测试

## 放在哪里

| 内容 | 目录 | 示例 |
| --- | --- | --- |
| 正式产品入口 | `firmware/<平台>/app/` | 主控程序、运动控制程序 |
| 独立烧录的硬件验证功能 | `firmware/<平台>/examples/<功能>/` | Wi-Fi 连接、编码器读取 |
| 平台内自动化单元测试 | `firmware/<平台>/tests/` | 状态机、命令调度 |
| 共享协议自动化单元测试 | `shared/protocol/tests/` | 编解码、边界值、损坏帧 |
| 跨板及系统集成测试 | `tests/integration/` | UART 联调、断线与重启 |
| 临时探索与验证 | `experiments/<主题>/` | 候选算法、尚未整理的原型 |

AS5600 PWM、目标命令解析、手动 EN 点动、PB5 使能、PB5 门控点动和位置／速度闭环已有六套主机测试，运行 `python3 tools/stm32.py test`。当前实机使用 `g431_closed_loop`；旧 `g431_motor_gpio` 保留为独立验证环境，步骤见 `firmware/stm32/examples/encoder_read/MOTOR_GPIO.md`，旧手动 EN 环境记录见 `MOTOR_JOG.md`。不同环境的 READY 只表示各自准备状态，不代表电机已实际运动。

本地角度调试台的测量解析、目标/使能/点动请求确认、高水位防重放、超时、HTTP 和串口生命周期测试位于 `tools/tests/`，使用 `.venv/bin/python -m unittest discover -s tools/tests -v`。2026-10-24 的工作树共 61 项 Python 测试通过，其中闭环专项 18 项；总数包含并行开发的机器人页面测试。这些测试不控制真实电机，串口集成使用系统伪终端。

## 新增上板测试功能

1. 在对应平台的 `examples/` 下建立按功能命名的目录，使用小写英文及下划线。
2. 按下方模板编写 README，写清硬件、接线、目标与验收方式。
3. 增加独立入口及构建配置，复用正式程序的驱动、协议与领域模块。不要复制驱动，也不要直接引用正式产品入口。
4. 确保构建时只选择一个入口；示例不得默认参与正式固件构建。
5. 上板后记录固件版本、硬件版本、配置及实测结果。未执行时明确标记，不填写推测结果。

同一功能由多人修改时共同维护同一目录，使用 Git 分支协作，不按人名创建平行副本。
框架和硬件明确后再补充实际构建入口，当前不提供无法运行的占位命令。

## 示例 README 模板

```markdown
# 功能名称

状态：待实现 / 待上板验证 / 已验证

## 目标
验证什么，预期结果是什么。

## 硬件与接线
板卡及版本、引脚、电源、外设和必要参数。

## 构建与烧录
实现后填写可复现的命令、工具链版本与目标板。

## 操作与验收
操作步骤、预期日志/观测值、通过标准和停止方式。

## 测试记录
日期、提交版本、硬件版本、配置、实际结果与已知问题。
```

## 自动化测试原则

对编解码、业务状态机和故障逻辑先写失败测试，再实现最小改动，最后重构。
测试围绕输入、状态与输出行为，不绑定私有实现细节。
平台无关逻辑使用可替换的时钟、传输与硬件接口，在主机上验证；需要板卡的测试须明确标注运行环境。
共享协议测试归共享模块维护，避免两端分别定义不同的期望值。
实机示例不替代自动化测试；单元测试通过也不代表电机和保护行为已经通过实机验证。

## 临时实验转正

实验应写清目的、负责人、依赖和当前结论。稳定且可复现的硬件演示移入对应 `examples/`；
可复用逻辑移入正式模块并补齐测试。正式固件不得依赖 `experiments/`。
